# Content strategy — SEO Phase 2

## Current site review

The site is a polished one-page React portfolio. It shows the developer name, full-stack role, React/React Native/Flutter/FastAPI/Node.js skills, six portfolio cards (wallet, logistics website, admin dashboard, social analytics dashboard, marketplace app and restaurant app), contact methods, a request form and English/French/Arabic interface copy. This supports a personal portfolio position and technology/project relevance.

The present copy is short and mostly generic. Project cards contain brief descriptions and feature bullets but no independently verifiable live demos, client attribution, dates, developer contribution, problem context, design/architecture decisions or measured result. “Leading logistics company” is an unsubstantiated superlative; prefer the neutral, existing “logistics company” wording unless evidence supports it. The site has no substantial AI content. The Opica Soft name/email exist, but the relationship to Mahamat and its offers are not described with enough evidence to position it as a company or agency for local searches.

## Content improvements implemented

- Made the hero H1 name the person and role, with English, French and Arabic wording following the selected UI language; kept its existing visual classes and layout.
- Updated the default document title and description to describe the actual developer portfolio and evidenced stack.
- Added language-aware title, description and Open Graph/Twitter title/description updates when a user changes the existing language selector.
- Existing in-page section navigation and contact/project calls to action provide internal links. No visual redesign, route, animation, integration or interaction was removed.

The page still has only one H1 and one canonical URL. Client-side language metadata changes may be seen after rendering but do not create three independently crawlable language documents.

## Recommended content roadmap

1. **Personal profile:** dedicated profile/about page with first-person biography, confirmed location (if the person wants to disclose it), experience, work preferences, verified professional links, and what the developer is looking for/offering. Do not invent years, certifications or client history.
2. **Mobile application development:** service page only after confirming active offer, supported platforms, engagement process, maintenance/support and original examples for both React Native and Flutter.
3. **Backend development:** explain actual API/backend work, integration scope, security/performance practices that can be evidenced, and project examples for FastAPI/Node.js.
4. **AI development:** do not publish yet. Add only when an original AI project/service is available to describe: user problem, model/provider or approach, data safeguards, testing/evaluation, limitations and the developer's exact contribution.
5. **Portfolio case studies:** create a dedicated page per project when verified details and media exist. Suggested structure: context and user need; status (concept, internal demo or shipped); Mahamat's role; architecture and selected technology rationale; key implementation; constraints; outcome with evidence; live demo/source link if public; client permission/attribution; next contact link. Never imply a concept is a deployed customer product.
6. **Opica Soft services:** first confirm whether this is Mahamat's business, employer, or simply a displayed brand. Then explain real service scope, delivery process, ideal customer, evidence, contacts, remote/local availability and service geography. Do not publish thin generic landing pages.

## Page structure and on-page guidance

For the current homepage, use one descriptive H1, then H2s for profile, skills, projects and contact; project names are H3s under the projects H2. Retain natural descriptions and meaningful image alt text. Add project-to-case-study links only when those pages exist. Link a verified service page from the corresponding skill/project, and give every future content page links to related evidence and the contact action. Avoid repetitive exact-match blocks.

For every future URL: write a distinct title and useful meta description; one accurate H1; an H2/H3 outline reflecting real visitor questions; descriptive link text; language-appropriate page copy; canonical to its own preferred URL; and reciprocal `hreflang` only when translated sibling URLs are maintained. Add structured data only when visible page content supports the properties.

## Professional authority opportunities

- Complete a GitHub profile README and pinned repositories with accurate descriptions, READMEs, screenshots, setup steps, architecture notes and licenses. Link only repositories the developer controls and is allowed to disclose.
- Create/complete a LinkedIn profile with a matching name, role, location only if accurate, project evidence and link to the portfolio. Add reciprocal links between public profiles and site.
- Build real project case studies with role, status, evidence, public demo/source where safe, and client approval before naming clients or displaying proprietary work.
- Request testimonials from actual clients/collaborators after work is complete. Get permission to publish exact quote, name, role and organization. Never fabricate testimonials or aggregate-rating markup.
- Participate in relevant Chad and regional developer communities, events and open source. Seek contextual citations from genuine project partners, professional associations, repositories, talks or profiles; do not buy links or mass-submit directories.

## Facts required before stronger local/service content

See `FACTS_TO_CONFIRM.md` for location, business identity/relationship, service scope, project status/rights and contact verification. An +235 phone number alone does not prove a physical address or city. Until facts are confirmed, prioritize the personal brand and portfolio projects rather than local business claims.
